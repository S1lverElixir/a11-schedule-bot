# Проверка бота расписания

Один прогон скрипта закрывает 90% вопросов; остальное — сетевые проверки с подводными камнями.

## Запуск

```bash
cd "<корень проекта>" && python -X utf8 .agents/skills/verify-bot/scripts/verify_bot.py
```

- Без аргументов: локальные проверки + сетевые (прод-бот, деплой, панель).
- `--local` — только локальные (без сети; когда не нужен прод или сеть недоступна).
- Код выхода 0 — красок нет. Скрипт печатает секции `ЛОКАЛЬНО` и `ПРОД` со строками
  `[OK] / [WARN] / [FAIL]`.

## Что проверяется

**Локально:** `rust/tools/check.py` целиком (сборка release, `cargo test`, паритет
против замороженных снимков, хеш и пик памяти `--selftest`); статические правила по
rust/src (нет chrono и async-рантайма, фиксированный UTC+3, фильтр владельца в двух
обработчиках, экранирование HTML, эмодзи в строках, CRLF и DTSTAMP в .ics, polling
без вебхука); данные (шесть официальных дат недель из таблицы bteu.by, полнота
SCHEDULE, покрытие KIND, границы семестра и якорь).

**Сеть:** прод-бот жив, если `getUpdates?timeout=25` даёт HTTP 409 (401 = невалидный
токен); статус последнего запуска deploy.yml через `gh run list --workflow=deploy.yml`;
состояние контейнера и память через API панели.

## Подводные камни (не «чинить» скрипт, они намеренные)

- **409-тест работает только с timeout≥5.** С `timeout=0/1` Telegram отвечает «OK»
  без конфликта — это ложное «бот мёртв». Скрипт использует 25 — не меняй.
- **Панель режет python-urllib через Cloudflare** — запросы только через curl с
  браузерным User-Agent (так в скрипте).
- **Снимки паритета заморожены:** Python-эталона в репозитории нет, поэтому зелёный
  паритет значит «Rust не изменил поведение», а не «Rust прав». У двух фоновых
  отправок (утренняя сводка, напоминание о сервере) покрытия нет вовсе.
- Нужен cargo: без Rust-тулчейна check.py падает FAIL, и это честно — локальной
  проверки бота больше нигде нет.

## Как интерпретировать и что говорить пользователю

- `FAIL` в ЛОКАЛЬНО — баг в данных или коде: чинить, коммитить, пушить, потом
  перегнать скрипт и проверить 409-тест.
- `FAIL` в ПРОД при зелёной локальной части — смотреть деплой (`gh run view <id> --log-failed`)
  и лог консоли панели (websocket; HTTP-эндпоинта логов нет). Частая причина —
  не продлён fps.ms («Add 24 hours» вручную раз в сутки).
- Итог для пользователя: одним абзацем — зелёное/красное, число пар и диапазон
  сегодня, память, статус деплоя, живость прод-бота. Без простыни сырых логов.
